# Verification Engine

The Verification Engine is a core backend component responsible for validating user-submitted evidence for sustainable actions.

## Principles
1. **Zero Client Trust**: The client is untrusted. Verification and state transitions happen strictly on the server.
2. **Authoritative Timestamps**: Action timestamps are generated by the server at the time of receipt.
3. **AI Assistance, Not Autonomy**: AI analyzes evidence but does not directly award points. It provides signals to the verification engine.

## States
An Action Submission can be in one of four states:
- `PENDING`: Initial state upon submission creation, awaiting evidence upload and finalization.
- `REVIEW_REQUIRED`: Signals were inconclusive or failed soft checks (like geofencing). Awaiting manual admin review.
- `VERIFIED`: Evidence confirmed by automated signals. Points awarded to the user.
- `REJECTED`: Evidence deemed invalid, duplicate, or fraudulent. No points awarded.

## Verification Signals
1. **AI Image Analysis**: Analyzes uploaded photos (e.g., verifying a picture actually contains a recycling bin or a reusable cup). Yields a confidence score.
2. **Geofencing**: Compares submitted coordinates against known campus sustainable zones (e.g., shuttle stops, recycling centers). Failures route the submission to `REVIEW_REQUIRED`.
3. **Duplicate Detection & Integrity**: Enforced strictly at the database level using a global unique constraint on the `sha256_hash` of uploaded files to prevent identical evidence reuse across the entire system.
4. **Storage Security**: Uploaded evidence files are sanitized and renamed using UUIDs to prevent Path Traversal attacks. Extensions are strictly vetted.

## Workflow
1. User creates an action submission via API (Status: `PENDING`).
2. User uploads evidence (photo, location, timestamp). Hashes are validated against the database unique constraints.
3. User finalizes the submission. The server locks the submission from further evidence uploads.
4. Server evaluates AI scores, geofence rules, and timestamp discrepancies.
5. If thresholds are met, state transitions to `VERIFIED` (and points are credited transactionally in later phases).
6. If signals are weak or geofence fails, it transitions to `REVIEW_REQUIRED` for admin manual review.
7. If duplicate rules or severe timestamp discrepancies occur, it transitions to `REJECTED`.
